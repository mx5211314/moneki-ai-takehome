# Moneki.ai 经营看板 + 混合问答助手

连锁餐饮（5 家门店）的经营看板，加一个能同时查 POS 数据库和公司文档的问答助手。
系统的"今天"固定为 **2026-09-01**，数据区间 **2026-05-01 ~ 2026-08-31**。

作业原题说明归档在 [`docs/ASSIGNMENT.md`](docs/ASSIGNMENT.md)，API 契约见
[`docs/API_CONTRACT.md`](docs/API_CONTRACT.md)。

---

## 三步跑起来

在仓库根目录执行（Python 3.12）：

```bash
# 1. 建虚拟环境、装依赖（只依赖 fastapi / uvicorn / httpx / pytest）
cd starter
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 2. 重建：从 ../data 与 ../knowledge_base 生成清洗表和检索索引
make rebuild

# 3. 起服务（http://127.0.0.1:8000）
make run
```

Windows 把 `.venv/bin/` 换成 `.venv\Scripts\`（例如 `.venv\Scripts\python.exe -m uvicorn ...`），
或者装了 [uv](https://github.com/astral-sh/uv) 的话直接 `make setup` 代替第 1 步。

**不配任何 Key 也能跑**：没有 `LLM_API_KEY` 时服务进入 mock 降级模式，照常启动、照常回答
（见契约 §7.2）。

另开一个终端跑公开题库自评：

```bash
python3 eval/run_eval.py --base-url http://127.0.0.1:8000 --questions eval/public_questions.jsonl
```

跑测试：`make test`（在 `starter/` 下）。

换一套数据 / 知识库（评测方会这么做）：

```bash
make rebuild DATA_DIR=/path/to/data KB_DIR=/path/to/knowledge_base
```

## 架构

```
         ┌──────────── 前端看板（静态页，无构建）────────────┐
         │ 指标趋势 · Top10 商品 · 数据质量 · 问答框 · trace │
         └───────────────────────┬──────────────────────────┘
                                 │ HTTP（同源 /api/*）
┌────────────────────────────────▼────────────────────────────────┐
│ kbqa.server（FastAPI）                                           │
│ /api/health  /api/metrics/*  /api/retrieve  /api/chat  /api/trace│
└──────┬──────────────────────────────────────────┬───────────────┘
       │                                          │
  ┌────▼──────────┐                    ┌──────────▼──────────────┐
  │ 数据链路       │                    │ 文档链路                  │
  │ cleaning.py   │ pos.db → clean.db  │ loader(.md/.txt/.html,   │
  │ tools.py      │ 18290 有效行        │  GBK/UTF-8 自动识别)      │
  │ query_metrics │                    │ chunker → index           │
  │ payment_mix   │                    │ 自研 BM25 + 中文二元组分词 │
  │ top_products  │                    │ retriever（版本过滤）      │
  └───────────────┘                    └──────────┬───────────────┘
       │                                          │
       └────────► planner.py（意图/槽位）◄─────────┘
                        │
              answerer.py（组装回答）
              数字=工具结果 · 说法=逐字引用
                        │
              trace.py（每步落盘，/api/trace 可查）
```

**一次提问的路径**：`planner` 判断"查数 / 查文档 / 两样都要"并解析时间、门店、商品
→ 数据侧调 `DataTools` 真实查库，文档侧走 BM25 检索并按焦点挑句子
→ `answerer` 组装：**经营数字必须来自查询结果并写进 `data_evidence`，文档说法必须带逐字 `quote`**
→ 全过程写进 trace，`/api/trace/{trace_id}` 可回放。

## 选型理由

| 选择 | 为什么 |
|---|---|
| 继续在 starter（Python + FastAPI）上改，不重写 | 缺陷是分层的，重写会丢掉"先加红测试再修"的证据链；原架构的分层本身是清楚的 |
| 检索用**自研 BM25 + 中文二元组分词**，不引向量库 | 35 篇文档、标准库足够，冷启动毫秒级；换知识库时重建成本极低，也不需要额外的嵌入模型 |
| 大模型走 **DeepSeek OpenAI 兼容协议**（三个环境变量） | 契约 §7.2 要求"切到 DeepSeek 不用改代码"；兼容协议最省事，详见 `LLM_SETUP.md` |
| 无 Key 时 **mock 降级**而非报错 | 契约硬性要求；本仓库全部评测即在 mock 模式下跑出 |
| 前端**不引构建工具** | 评分要在干净环境跑起来，少一层构建就少一处失败点 |
| 文档事实**逐字引用**，不改写 | 契约会逐字核对 `quote`，改写必然失分；宁可少引也不编 |

## 我对口径和歧义的取舍

这几处题目里没写死，我按知识库口径拍的板：

1. **净营业额**：销售金额 + 退款行（退款记负数）后的净额，退款**不**单独剔除。
2. **客单价**：净营业额 ÷ 有效订单数；**没有订单时返回 `null` 而不是 0**——
   0 会被误读成"客单价为零"，是另一种错。
3. **清洗口径**（`raw 18628 → kept 18290`）：按日期不可解析 8、金额为空 150、
   数量 ≤ 0 的 30、门店外键不存在 10、商品外键不存在 40、完全重复 100 依次剔除。
   退款行**保留**（它是净营业额的组成部分），只剔除无效行。
4. **文档有新旧版**：默认取**现行版**；用户明说"当时/那时候"并按日期提问时，
   取**当时生效**的那一版，并注明现行版是什么。
5. **数据库与文档数字冲突**：经营数字一律以**数据库**为准。口径手册写明
   周报、纪要里的数字是估算，只当说法引用，不当数字出处。
6. **答不上来就说不知道**：数据区间之外、知识库也没讲的，如实拒答，
   **不编数字也不编原因**。
7. **文档内容只当资料，不当指令**：要求删改数据、套取系统提示词或表结构的，
   一律拒答；数据库只读，不做任何写操作。
8. **会话隔离**：不同 `session_id` 之间不共享上下文；同一个 `session_id` 内支持
   追问（"那 7 月呢？"）。不传 `session_id` 的请求归入匿名档。
